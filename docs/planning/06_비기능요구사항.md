# Opiki 비기능 요구사항 (NFR)

## 1. 성능

| 항목 | 기준(제안) |
|---|---|
| 혜택 목록/검색 응답 | 1초 이내 |
| AI 요약 생성 | 최초 생성 시 3~5초 허용, 이후 캐시로 즉시 응답 |
| 맞춤 추천 목록 로딩 | 2초 이내 |
| 동시 사용자 처리 | 초기 목표 100~500명 동시 접속 기준 설계 (학생 프로젝트/데모 규모) |

## 2. 보안 / 개인정보

- 사용자 프로필(나이/소득/학교/거주지)은 민감도 높은 개인정보 → 암호화 저장(특히 소득 구간) 및 접근 로그 관리
- 로그인 토큰(JWT) 만료/재발급 정책 수립
- 개인정보처리방침 및 이용약관 사전 고지 (특히 소득/거주지 수집 근거 명시)

## 3. 알림 관련 정책

- 푸시 알림 발송 실패 시 재시도 정책(예: 3회, exponential backoff)
- 사용자가 알림 수신을 거부한 경우에도 인앱 알림 센터에는 기록 유지
- 마감 임박 알림 기준일(D-day)은 사용자가 설정 가능하도록 (기본값 제안: D-3)

## 4. 데이터 최신성

- 혜택 공고 데이터 갱신 주기: 최소 1일 1회 배치 동기화 권장
- 마감된 공고는 자동으로 "마감" 상태 처리, 추천/배너 노출에서 제외

## 5. 접근성 / 사용성

- 온보딩 단계 최소화(이탈 방지): 필수 항목(나이/거주지) 우선, 소득/학교는 선택 입력 후 점진적 수집 고려
- 상세/요약 토글은 1탭으로 전환 가능해야 함
- 캘린더 뷰는 마감 임박 항목을 시각적으로 강조(색상/뱃지)

## 6. 확장성 / 유지보수

- 혜택 자격조건(JSON) 구조는 새로운 조건 유형 추가가 쉬운 형태로 설계 (스키마 하드코딩 지양)
- AI 프롬프트/로직은 별도 서비스 레이어로 분리하여 모델 교체(예: 타 LLM 전환) 시 영향 최소화

## 7. 법적/제도적 고려사항

- 청년 혜택 정보의 출처 표기 및 원문 링크 필수 제공(정보 정확성 책임 범위 명시)
